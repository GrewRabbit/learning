# 代码审核 r1 修复 - AI 服务模块

**日期**：2026-07-06
**类型**：优化
**影响范围**：`app/lib/ai/services/` 与 `app/lib/ai/clients/` 目录（共 8 个原文件 + 5 个新拆分文件）

## 变更背景

第 1 轮全量代码审核（[code-review-full-r1.md](../reviews/code-review-full-r1.md)）针对 AI 服务模块提出 9 项必修复问题（P0+P1：CR1-001/002/004/005/006/012/013/014/015）与 2 项 P2 可选问题（CR1-017/018）。本次按审核意见修复全部 9 项必修复问题，P2 项推迟处理（理由见末尾）。

核心驱动：
- **G3 硬性约束**：单文件 ≤ 500 行（`orchestrator.ts` 655 行、`fs-html-cache.ts` 568 行均超限）
- **类型安全**：消除 `as unknown as` 双重断言、`!` 非空断言、`role: string` 过宽类型
- **可移植性**：消除硬编码绝对路径与二进制名
- **日志规范**：服务端 `console.warn` 全部替换为 `logger.warn`（`dev-workflow.md` §六）

## 变更内容

### CR1-015 + CR1-005：llm-client.ts 类型修复

- 将 `type ChatMessage = { role: string; content: string }` 改为 discriminated union：
  ```typescript
  type ChatMessage =
    | { role: 'system'; content: string }
    | { role: 'user'; content: string }
    | { role: 'assistant'; content: string };
  ```
- 移除 `messages as unknown as OpenAI.Chat.Completions.ChatCompletionMessageParam[]` 双重断言，改为直接赋值 `messages,`
- 联合类型按字面量匹配 `ChatCompletionMessageParam` 联合成员，无需逃逸

### CR1-004：llm-caller.ts 图片消息 text 字段 Bug

- 图片场景下 `input.problem.content` 为 base64 图片数据，原写法 `text: input.problem.content || '请识别图片中的题目内容'` 会让 LLM 收到 `text=<base64 串>` 浪费 token 且干扰理解
- 改为固定描述文本 `{ type: 'text', text: '请识别图片中的题目内容' }`，图片数据通过 `image_url` 字段传递

### CR1-014：orchestrator.ts 非空断言移除

- `const data = validateResult.data!;` 改为显式 if 检查：
  ```typescript
  if (!validateResult.data) { return '验证结果数据缺失'; }
  const data = validateResult.data;
  ```
- 同步迁移至 `format-errors.ts`（见 CR1-001 拆分）

### CR1-012：html-cache.ts 硬编码绝对路径

- `'/var/learning/data/gesp6'` 改为 `path.resolve(process.cwd(), 'data/gesp6')`
- 添加 `import path from 'path';`
- 仍可通过 `GESP6_CACHE_FS_DIR` 环境变量覆盖默认值

### CR1-013：code-validator.ts g++-13 抽取为常量

- 新增模块常量 `const GPP_BINARY = process.env.GESP6_GPP_BINARY ?? 'g++-13';`
- 替换所有 `g++-13` 引用：`execFile` 参数、`cmd` 模板字符串、日志消息、错误消息
- 注释中的说明性文字（如"通过 PPA 安装 g++-13"）保留

### CR1-006：服务端 console.warn → logger.warn（5 处）

- `youdao-fetcher.ts`（2 处）：HTML 长度截断警告 + 通用选择器回退警告
- `image-recognizer.ts`（1 处）：识别 Prompt 文件不存在回退
- `orchestrator.ts`（2 处）：解析失败降级 + 主 key 回填跳过（CR1-001 拆分后保留在 orchestrator）
- 各文件顶部已正确 import `logger`，参数保持不变

### CR1-001：orchestrator.ts 拆分（655 → 454 行）

按评审建议拆分，并在评审建议基础上额外拆出 `fix-loop.ts` 以满足 G3 ≤500 硬性约束：

- 新增 [format-errors.ts](../../app/lib/ai/services/format-errors.ts)（41 行）：导出 `formatErrors(validateResult)`，含 CR1-014 显式检查
- 新增 [prompt-loader.ts](../../app/lib/ai/services/prompt-loader.ts)（72 行）：导出 `PromptLoader` 类 + `promptLoader` 单例，迁移 `SKILL_PROMPT_PATH`/`KNOWLEDGE_BASE_PATH` 常量与 `loadSkillPrompt()`/`loadKnowledgeBase()` 方法
- 新增 [fix-loop.ts](../../app/lib/ai/services/fix-loop.ts)（222 行）：导出 `runFixLoop(input: FixLoopInput)` + `FixLoopInput` 接口，迁移修正循环逻辑（for 循环 + g++ 降级 + 解析 + 重新验证）
- 保留 [orchestrator.ts](../../app/lib/ai/services/orchestrator.ts)（454 行）：核心编排流程，调用 `promptLoader.loadSkillPrompt()` / `promptLoader.loadKnowledgeBase()` / `runFixLoop({...})`

> **额外拆分说明**：评审 CR1-001 仅建议拆出 format-errors + prompt-loader，但拆分后 orchestrator.ts 仍 576 行超 G3 限制。修正循环作为"步骤5"边界清晰、测试覆盖充分，故额外拆出 `fix-loop.ts`（减约 110 行），最终 454 行满足约束。

### CR1-002：fs-html-cache.ts 拆分（568 → 486 行）

按评审 CR1-002 建议拆分路径计算与 JSON IO 工具：

- 新增 [fs-paths.ts](../../app/lib/ai/services/fs-paths.ts)（96 行）：路径计算函数（`getPrimaryIndexPath`/`getContentHtmlPath`/`getContentMetaPath`/`getSampleIndexPath`）+ `PRIMARY_KEY_PREFIX` 常量 + `PrimaryIndex`/`SolutionMeta`/`SampleIndex` 接口 + `buildPrimaryKey`/`parsePrimaryKey`/`getCandidateFingerprints` 工具
- 新增 [fs-json-io.ts](../../app/lib/ai/services/fs-json-io.ts)（42 行）：`ensureDirSync` + `readJsonSync<T>` + `writeJsonAsync` IO 工具
- 保留 [fs-html-cache.ts](../../app/lib/ai/services/fs-html-cache.ts)（486 行）：`FsHtmlCache` 主类，调用新模块函数（路径计算函数需传入实例 `primaryDir`/`contentDir`/`sampleDir`）

> **额外迁移说明**：评审 CR1-002 仅明确指出 4 个路径函数与 2 个 IO 函数。为达成 ≤500 行约束，额外将 `PRIMARY_KEY_PREFIX` 常量、3 个索引接口、`parsePrimaryKey`/`getCandidateFingerprints` 工具一并迁入 `fs-paths.ts`（均为纯函数/纯类型，无副作用，迁移后 fs-html-cache.ts 主类更聚焦于缓存策略）。`writeJsonAsync` 用于 `writeAsync`/`writeContentFiles`（meta）/`writeSampleIndex` 三处 JSON 写入；HTML 原始写入（非 JSON）仍保留 `fsAsync.writeFile`。

### 后续关注点

1. **fix-loop.ts 边界**：拆分后 `runFixLoop` 通过 `FixLoopInput` 接口接收依赖（caller/parser/validator/meta/html/validateResult/computeStartTs），调用方 orchestrator.ts 负责组装。如后续修正循环策略变更（如改用 LLM 自我反思），仅需修改 `fix-loop.ts` 不影响编排流程。
2. **fs-paths.ts 复用**：路径计算与索引结构现为独立模块，未来 `DbHtmlCache`（架构 §8.3 预留）或迁移工具可复用 `parsePrimaryKey`/`buildPrimaryKey` 与索引类型定义，无需依赖 `FsHtmlCache` 类。
3. **writeJsonAsync 一致性**：三处 JSON 写入（writeAsync 主索引 / writeContentFiles meta / writeSampleIndex）均改为 `writeJsonAsync`，HTML 原始写入保留 `fsAsync.writeFile`。若未来需要统一 fire-and-forget 调度策略，可考虑在 `fs-json-io.ts` 增加 `writeJsonFireAndForget` 高阶工具。
4. **GPP_BINARY 环境变量**：部署文档与 `.env.local.example` 应补充 `GESP6_GPP_BINARY` 说明（本次仅改代码，未改示例文件，避免与 DevOps 模块改动冲突）。
