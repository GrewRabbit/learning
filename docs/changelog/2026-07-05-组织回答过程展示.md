# 思考过程与组织回答过程双面板展示

**日期**：2026-07-05
**类型**：优化
**影响范围**：任务队列（job-store）、API 接入层（/api/solve）、题目录入页（/solve）

## 变更背景

前期已实现 GLM-5.x thinking 模式下的"思考过程"前端展示（reasoning_content 累积）。但 onChunk 回调仅处理 `reasoning` 片段，忽略 `content` 片段。导致用户观察到：

- 思考阶段（reasoning_content）结束后，进入回答阶段（content），此时前端 thinking 面板不再更新
- 由于 content 阶段前端不可见，用户感觉"AI 思考完成后到 HTML 生成完成之间在长时间等待"（实际 content 阶段正在生成 24K+ 字符的 HTML）
- 例如 Terminal#960-961 任务，elapsedMs:691565（≈11.5 分钟）期间，content 阶段前端无任何进度反馈

为提升用户感知，将原本单一"思考过程"面板拆分为两个面板：
1. **AI 思考过程**：reasoning_content 累积（与原方案一致）
2. **AI 组织回答**：content 累积（思考阶段结束后开始，前端通过 organizingContent 是否有内容判定切换面板）

两个面板均受 `GESP6_THINKING_DISPLAY_ENABLED` 环境变量统一管理。

## 变更内容

### 后端：JobStore 新增 organizingContent 字段

- **job-store.ts**：`JobRecord` 新增 `organizingContent: string` 字段（`createJob` 初始化为 `''`）
- **job-store.ts**：新增 `appendOrganizingChunk(id, text)` 函数累积 content 片段，与 `appendThinkingChunk` 对称；设 `ORGANIZING_CONTENT_MAX_LENGTH = 200_000` 上限防止超大 content 撑爆内存

### 后端：route.ts onChunk 处理 content 类型

- **route.ts POST**：`onChunk` 回调扩展为处理两种 chunk 类型：
  - `type === 'reasoning'` → 调用 `appendThinkingChunk`（累积到 thinkingContent）
  - `type === 'content'` → 调用 `appendOrganizingChunk`（累积到 organizingContent）
- **route.ts GET**：`processing` 和 `done` 状态均返回 `organizingContent` 字段，供前端轮询实时展示
- **环境变量控制不变**：`GESP6_THINKING_DISPLAY_ENABLED=false` 时 onChunk 为 undefined，两个面板都不展示（与原方案一致，无需新增环境变量）

### 前端：组织回答折叠面板

- **solve/page.tsx**：新增 `organizingContent` 和 `showOrganizing` state；`pollJob` 从响应中提取 `organizingContent` 并更新 state；`handleSubmit` 重置 organizingContent 和 showOrganizing
- **solve/page.tsx**：loading 状态下展示"AI 组织回答"折叠面板（紧贴"AI 思考过程"面板下方），含 `PenLine` 图标 + 字数统计 + `ChevronDown/ChevronRight` 展开切换；展开时在 `max-h-96` 滚动区域内用 `<pre>` 展示组织回答内容
- **图标选择**：思考过程用 `Brain`，组织回答用 `PenLine`，便于用户区分两个阶段

### 阶段切换逻辑

GLM-5.x thinking 模式两阶段输出特性保证：
1. **阶段 1（思考）**：仅产生 `reasoning_content` chunk → thinkingContent 累积，organizingContent 为空
2. **阶段 2（组织回答）**：仅产生 `content` chunk → organizingContent 开始累积

前端通过 `organizingContent` 是否有内容自然判定思考阶段已结束，无需显式阶段标志位。两个面板均会在 loading 期间持续展示，直到任务完成跳转 /result。

## 配置 / 环境变量变化

无新增环境变量。两个面板均受现有 `GESP6_THINKING_DISPLAY_ENABLED` 控制：

| 变量名 | 默认值 | 说明 |
|--------|--------|------|
| `GESP6_THINKING_DISPLAY_ENABLED` | `true` | 思考过程与组织回答前端展示开关。设为 `false` 时同时关闭两个面板（onChunk 不传，thinkingContent/organizingContent 均不累积） |

## 后续影响 / 注意事项

1. **响应体大小增加**：每次轮询返回 thinkingContent + organizingContent 两个累积字符串，最大各 200K，极端场景下响应体可达 400K+；如遇性能问题可改为增量协议
2. **阶段切换的"自然判定"特性**：依赖 GLM-5.x thinking 模式两阶段输出顺序（先 reasoning 后 content），若切换到非 thinking 模型（如 DeepSeek v4 非 thinking 模式），organizingContent 会从一开始就有内容，思考面板不会展示——这是预期行为
3. **ORGANIZING_CONTENT_MAX_LENGTH = 200_000**：超过此上限后静默丢弃后续 content 片段，防止内存溢出；最终 HTML 仍通过 result 完整返回，不影响功能
4. **向后兼容**：onChunk 仍为可选参数，未传时 llm-caller 正常工作；现有调用方无需修改
5. **图片识别路径不受影响**：image-recognizer 未传 onChunk，图片识别阶段不展示思考/组织回答面板，与原方案一致
