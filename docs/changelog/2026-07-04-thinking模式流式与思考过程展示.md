# GLM-5.x thinking 模式流式调用与思考过程前端展示

**日期**：2026-07-04
**类型**：优化 + 新增
**影响范围**：LLM 调用层（llm-caller）、编排层（orchestrator）、任务队列（job-store）、API 接入层（/api/solve）、题目录入页（/solve）

## 变更背景

前期 GLM-5.2 调用频繁超时（`GESP6_LLM_TIMEOUT`，elapsedMs > 120s）。经 curl 直测与 Context7 查询 GLM 官方文档定位根因：

1. **GLM-5.x 默认开启 thinking 模式**：生成 `reasoning_content`（思考过程）后再生成 `content`（最终回答），总耗时可达 180s+
2. **非流式调用 + 120s 超时**：非流式必须等待 ALL content（reasoning + final）才返回，28K 字符 skill prompt 导致 reasoning_tokens 爆炸，超过 120s 总超时
3. **思考过程被丢弃**：thinking 模式产生的 reasoning_content 未传递到前端，用户无法看到 AI 思考过程

## 变更内容

### 第一步：流式调用 + 开启 thinking + 调整超时

- **llm-caller.ts**：`callOnce` 改为 `stream: true`，通过 `for await` 遍历 chunk 累积 `delta.content`；流式保持连接活跃，避免非流式模式下总耗时超 timeout
- **llm-caller.ts**：`LLM_TIMEOUT_MS` 从 `120_000` 调整为 `300_000`（300s 兜底，防止模型卡死时无限等待）；移除 `thinking: { type: 'disabled' }` 参数（GLM-5.x 默认开启 thinking，无需显式传参）
- **llm-caller.test.ts**：新增 `mockStream()` 辅助函数模拟 OpenAI SDK 流式 async iterable；所有 10 处 mock 返回值从 `{ choices: [{ message: { content } }] }` 改为 `mockStream(content)`

### 第二步：思考过程前端展示

#### 数据链路（onChunk 回调）

- **types.ts**：新增 `LLMChunk` 类型（`{ type: 'reasoning' | 'content'; text: string }`）；`LLMInput` 增加可选 `onChunk` 回调字段
- **llm-caller.ts**：`callOnce` 流式循环中，对 `delta.reasoning_content` 调用 `input.onChunk?.({ type: 'reasoning', text })`，对 `delta.content` 调用 `input.onChunk?.({ type: 'content', text })`；未传 onChunk 时忽略（向后兼容）
- **orchestrator.ts**：`solve`/`solvePlatform`/`solveTextOrImage`/`compute`/`callFix` 均增加可选参数 `onChunk?: (chunk: LLMChunk) => void`，透传到 3 处 `caller.generate()` 调用（主生成、格式重试、修正循环）
- **job-store.ts**：`JobRecord` 新增 `thinkingContent: string` 字段（`createJob` 初始化为 `''`）；新增 `appendThinkingChunk(id, text)` 函数累积 reasoning 片段；设 `THINKING_CONTENT_MAX_LENGTH = 200_000` 上限防止超大 thinking 撑爆内存
- **route.ts POST**：构造 `onChunk` 回调，仅对 `type === 'reasoning'` 的 chunk 调用 `appendThinkingChunk(jobId, chunk.text)`（content 片段不存，最终 HTML 已在 result 中）；传入 `gesp6Orchestrator.solve(problem, shouldAbort, onChunk)`
- **route.ts GET**：`processing` 和 `done` 状态均返回 `thinkingContent` 字段，供前端轮询实时展示

#### 前端展示（折叠面板）

- **solve/page.tsx**：新增 `thinkingContent` 和 `showThinking` state；`pollJob` 从响应中提取 `thinkingContent` 并更新 state；`handleSubmit` 重置 thinkingContent 和 showThinking
- **solve/page.tsx**：loading 状态下展示思考过程折叠面板（默认折叠），含 `Brain` 图标 + 字数统计 + `ChevronDown/ChevronRight` 展开切换；展开时在 `max-h-96` 滚动区域内用 `<pre>` 展示思考内容

### 第三步：思考过程展示开关（环境变量配置）

- **route.ts POST**：新增 `GESP6_THINKING_DISPLAY_ENABLED` 环境变量判断（默认 `true`）；设为 `false` 时 onChunk 传 `undefined`，从源头不累积 thinkingContent，前端面板自然不展示
- **.env.local**：新增 `GESP6_THINKING_DISPLAY_ENABLED=true` 配置项（含注释说明）

## 后续影响 / 注意事项

1. **GLM-5.x thinking 模式总耗时仍可能 180s+**：流式调用避免总超时问题，但前端仍需展示"已等待 X分Y秒"安抚用户
2. **thinkingContent 响应体大小**：当前每次轮询返回完整累积的 thinkingContent（非增量），超大 thinking 场景下带宽消耗较大；如遇性能问题可改为增量协议（`?since=chunkIndex`）
3. **THINKING_CONTENT_MAX_LENGTH = 200_000**：超过此上限后静默丢弃后续 reasoning 片段，防止内存溢出
4. **image-recognizer 未传 onChunk**：图片识别的 thinking 过程不展示（仅解题 thinking 有价值），设计上保持不变
5. **向后兼容**：onChunk 为可选参数，未传时 llm-caller 正常工作；现有调用方（如 smoke-runtime 烟测）无需修改
