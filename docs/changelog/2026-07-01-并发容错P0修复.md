# 并发容错 P0 修复：LLM 指数退避重试 + 限流阈值调整

**日期**：2026-07-01
**类型**：优化
**影响范围**：app/lib/ai/services/llm-caller.ts、middleware.ts、对应单元测试

## 变更背景

并发访问评估发现两个 P0 级问题：

1. **LLM 调用无重试机制**：[llm-caller.ts](file:///var/learning/app/lib/ai/services/llm-caller.ts) 中 `maxRetries: 0`，LLM 服务方返回 429（限流）或网络抖动时直接失败，用户看到 `GESP6_INTERNAL_ERROR` 错误页。多用户并发场景下，DeepSeek/Qwen 的 QPS 限制（默认 60 req/min）容易触发，导致用户体验差。

2. **限流阈值偏低**：[middleware.ts](file:///var/learning/middleware.ts) 限流 5 次/分钟/IP，但 1 题最多消耗 4 次 LLM 调用（生成 1 次 + 修正循环 3 次），单用户每分钟仅能完成 1 题多一点，正常使用场景下极易触发限流。

## 变更内容

### LLMCaller 应用层指数退避重试

[llm-caller.ts](file:///var/learning/app/lib/ai/services/llm-caller.ts) 重构：

- 提取核心调用逻辑为私有方法 `callOnce`（不含重试）
- `generate` 方法添加应用层重试循环：
  - **可重试错误**：`RateLimitError`（429）、`APIConnectionError`（网络抖动）
  - **不重试错误**：`APIConnectionTimeoutError`（已超时）、其他错误（如认证失败）
  - **重试策略**：指数退避 1s → 2s → 4s，最多 3 次重试
  - **总最大时长**：120s 超时 + 7s 重试等待 ≈ 127s
- SDK 层 `maxRetries: 0` 保留（避免 SDK 自动重试与应用层重试叠加）

错误处理流程：
```
callOnce 抛错
  ├─ isTimeoutError → 返回 GESP6_LLM_TIMEOUT（不重试）
  ├─ isRetryableError && attempt < 3 → sleep(2^attempt s) → 重试
  └─ 其他 / 重试耗尽 → 返回 GESP6_INTERNAL_ERROR
```

### middleware 限流阈值调整

[middleware.ts](file:///var/learning/middleware.ts)：

- `RATE_LIMIT_MAX`：5 → 20
- 配额消耗说明：1 题最多 4 次 LLM 调用（生成 1 次 + 修正循环 3 次），20 次配额允许单用户每分钟最多 5 题并发
- 错误提示文案同步更新："每分钟最多 5 次" → "每分钟最多 20 次"

### 单元测试更新

#### middleware.test.ts

- "单 IP 第 6 次请求返回 429" → "单 IP 第 21 次请求返回 429"
- "x-forwarded-for 优先级" 用例：调用次数 6 → 21（适配新阈值）

| 用例 | 验证点 |
|------|--------|

## 后续影响 / 注意事项

1. **重试与 Orchestrator 修正循环的关系**：LLMCaller 重试针对**单次调用**的 429/网络错误；Orchestrator 修正循环针对**输出不合格**的修正。两者职责分离，不冲突
2. **重试总时长上限**：单次 LLM 调用超时 120s + 3 次重试等待 7s = 127s。若 LLM 服务方持续 429，最坏情况用户等待约 127s 才看到错误页
3. **限流阈值与 LLM 服务方 QPS 的关系**：项目限流 20 次/分钟/IP 是**入口限流**，LLM 服务方 QPS 限制（如 DeepSeek 60 req/min）是**全局限制**。多用户并发时，即使每个用户都在项目限流内，总和仍可能超过 LLM 服务方 QPS，此时由 LLMCaller 重试机制兜底
4. **fake timers 测试**：LLM 重试测试用 `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync()` 推进时间，避免真实等待 7s。注意 `afterEach` 中 `vi.useRealTimers()` 恢复，避免影响后续测试
5. **类型断言绕过 mock 签名差异**：测试中 `OpenAI.RateLimitError as unknown as new (m: string) => Error` 是必要手段，因 tsc 用真实 SDK 类型（构造函数需 4 参数），而运行时 mock 仅需 1 参数
