# Solve 路由建档计费整合

**日期**：2026-08-19
**类型**：新增
**影响范围**：`POST /api/solve`（建档前置 + 完成回调计费）、`GET /api/solve`（done 响应新增计费字段）、`app/api/solve/`、`app/lib/billing/`（仅消费，未修改）

## 变更背景

实施数据库与业务系统整合架构（arch-db-integration-v1.1）步骤 7：将已就绪的 `userDao.getOrCreateUser`（T1）与 `billingService.settleSuccessfulSolution`（T3）接入 solve 路由，完成「认证 → 建档 → 解题 → 原子计费 → 结果透出」全链路（FR-027/FR-028/FR-022）。

## 变更内容

### POST /api/solve 建档整合（FR-027）

- 流程调整为：认证 → Zod → resolvePlatform → **建档** → createJob。与架构 §4.1（认证→建档→Zod）顺序差异：建档后置到全部输入校验通过之后，避免非法输入白白触发 DB 往返；「建档失败不建 job、不触发 LLM」（AC-001）语义不变
- 建档失败分支：`GESP6_DB_UNAVAILABLE` → 503（不创建 job、不触发 LLM）；其余（`GESP6_USER_CREATE_FAILED` 等）→ 500；`GESP6_BILLING_DEGRADE_OPEN=1`（fail-open）→ 放行 `userId=null` 继续流程 + WARN（AR1-006）
- 新增模块级 `getFreeQuotaInitial()`：`GESP6_FREE_QUOTA_INITIAL` 解析（默认 5，非正整数回退默认）

### 完成回调计费整合（FR-028，提取为 settle-callback.ts）

- `.then` 回调 async 化，成功且未取消分支按序处理：前置取消检查（AR1-005，现状保留）→ `userId=null` 跳过 DB 直接 `completeJob(charged=false, balanceRemaining=null)` → `settleSuccessfulSolution`（透传 userId/contentHash/jobId/inputType/platform/problemId/sampleFp/cached/validated）
- settle 成功 → `completeJob` 第三参透传 `charged`/`balanceRemaining`；额度不足 / 其他计费失败 → `failJob`（不返回解法，settle 事务已回滚未写记录）
- 计费 DB 故障（`GESP6_BILLING_DB_UNAVAILABLE` / `GESP6_DB_UNAVAILABLE`）：默认 fail-closed → `failJob`；fail-open=1 → `completeJob` 放行（不计费不写任何 DB 记录）+ WARN（AC-026）
- settle 抛意外异常由外层 `.catch` 兜底转 `failJob(GESP6_INTERNAL_ERROR)`，不悬挂 promise
- `isBillingDegradeOpen()` 定义于此模块并导出（每次读取 env，便于运行时切换与测试 stubEnv）

### GET 轮询透出（FR-022/AR1-007）

- done 响应 data 顶层新增 `charged: boolean` 与 `balanceRemaining: number | null`（与 result 平级；null=额度暂不可用，fail-open 放行期间）
- GET 无鉴权、error envelope 维持 200，均维持现状
