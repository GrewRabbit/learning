# 并发容错 P1 修复：LLM 与 g++ 编译全局并发限制

**日期**：2026-07-01
**类型**：新增
**影响范围**：app/lib/ai/services/concurrency-limiter.ts（新增）、llm-caller.ts、code-validator.ts、对应单元测试

## 变更背景

并发容错 P0 修复（重试 + 限流）已上线，但并发场景评估发现两个 P1 级问题：

1. **LLM 调用无并发上限**：[llm-caller.ts](file:///var/learning/app/lib/ai/services/llm-caller.ts) 中 `generate()` 直接发起调用，无全局并发控制。多用户并发访问时，会同时发起多个 LLM 请求，触发 LLM 服务方 QPS 限制（如 DeepSeek 60 req/min）。虽然 P0 已加重试兜底，但持续高并发会让重试也失败，最终用户看到错误页。

2. **g++ 编译无并发上限**：[code-validator.ts](file:///var/learning/app/lib/ai/services/code-validator.ts) 中 `validate()` 直接发起编译，无全局并发控制。g++ 是 CPU 密集型操作（每次编译最多 10s CPU），并发编译会耗尽服务器 CPU 资源，影响其他请求响应。

## 变更内容

### 新增 ConcurrencyLimiter 通用并发限制器

[concurrency-limiter.ts](file:///var/learning/app/lib/ai/services/concurrency-limiter.ts) 新建：

- 通用 Promise 并发限制器（FIFO 队列，无外部依赖）
- API 设计：
  - `run<T>(fn: () => Promise<T>): Promise<T>` — 包裹任务在并发限制内执行
  - `getActiveCount(): number` — 当前活跃任务数（用于监控）
  - `getQueueLength(): number` — 当前排队任务数（用于监控）
- 工作原理：active < max 时立即执行；active >= max 时入队等待；任务完成后按 FIFO 唤醒下一个
- 错误传播：任务抛错时错误原样传播，不影响 active 计数与队列唤醒

```typescript
export class ConcurrencyLimiter {
  private active = 0;
  private readonly queue: Array<() => void> = [];

  constructor(private readonly maxConcurrent: number) {}

  async run<T>(fn: () => Promise<T>): Promise<T> {
    if (this.active >= this.maxConcurrent) {
      await new Promise<void>((resolve) => this.queue.push(resolve));
    }
    this.active++;
    try {
      return await fn();
    } finally {
      this.active--;
      const next = this.queue.shift();
      if (next) next();
    }
  }
}
```

### LLMCaller 添加全局并发限制

[llm-caller.ts](file:///var/learning/app/lib/ai/services/llm-caller.ts)：

- 新增模块级常量 `LLM_MAX_CONCURRENT = 3`
- 新增模块级单例 `llmLimiter = new ConcurrencyLimiter(LLM_MAX_CONCURRENT)`
- `generate()` 重构：原直接调用 `generateWithRetry()` → 现用 `llmLimiter.run(() => this.generateWithRetry(input))` 包裹
- 设为 3 的原因：
  - LLM 服务方默认 QPS 限制 60 req/min，3 个并发在 120s 超时窗口内最多 3 次调用，远低于限制
  - 避免应用层并发触发 LLM 服务方限流（与 P0 重试配合，限流时由重试兜底）
  - 给 LLM 服务方留余量，避免被识别为恶意流量

### CodeValidator 添加全局并发限制

[code-validator.ts](file:///var/learning/app/lib/ai/services/code-validator.ts)：

- 新增模块级常量 `COMPILE_MAX_CONCURRENT`（环境变量 `GESP6_COMPILE_CONCURRENCY` 配置，默认 2）
- 新增模块级单例 `compileLimiter = new ConcurrencyLimiter(COMPILE_MAX_CONCURRENT)`
- `validate()` 重构：
  - g++ 可用性检查（`checkGppAvailable`）不受并发限制（仅快速检查）
  - 实际编译+运行逻辑提取为私有方法 `validateInternal`
  - 用 `compileLimiter.run(() => this.validateInternal(...))` 包裹
- 设为 2 的原因：
  - g++ 编译是 CPU 密集型操作，过多并发会耗尽 CPU
  - 单核服务器 2 个并发编译已接近上限（每个编译最多 10s CPU）
  - 多核服务器可通过环境变量 `GESP6_COMPILE_CONCURRENCY` 调高

### 单元测试

#### concurrency-limiter.test.ts（新建，6 用例）

| 用例 | 验证点 |
|------|--------|
| 并发数不超过上限 | max=2 时并发 3 个任务，active 永远 ≤ 2 |
| FIFO 顺序 | 任务按入队顺序依次执行 |
| 任务完成唤醒下一个 | 前置任务 resolve 后队列下一个任务立即开始 |
| 错误传播 | 任务抛错时错误原样传播，active 计数与队列正确 |
| getActiveCount 与 getQueueLength | 状态查询准确（task1+task2 active=2，task3 排队） |
| maxConcurrent=1 串行 | 退化为串行执行 |

> 测试关键点：用可控 Promise（保存 resolve 回调）替代 `Promise.resolve()`，避免立即完成导致 active 计数不准确。

## 后续影响 / 注意事项

1. **并发限制与重试的关系**：P0 的 LLM 重试针对**单次调用**的 429/网络错误；P1 的并发限制针对**全局并发数**。两者协同：并发限制降低触发 429 的概率，重试兜底偶发的 429
2. **模块级单例的生命周期**：`llmLimiter` 与 `compileLimiter` 是模块级单例，整个 Node.js 进程内共享。Next.js 多 worker 模式下每个 worker 独立计数（与 middleware 的 ipRequestMap 一致），多机部署需切换到 Redis 计数
3. **g++ 并发上限可调**：通过 `GESP6_COMPILE_CONCURRENCY` 环境变量配置。建议值 = min(CPU 核数, 4)。设置过高会导致 CPU 争抢，反而降低吞吐
4. **测试技巧**：ConcurrencyLimiter 测试用可控 Promise（保存 resolve 回调）替代 `Promise.resolve()`，是验证 active 计数与队列唤醒的关键。立即完成的任务会让 active 在 await 前已递减，导致断言失败
5. **未来扩展**：若需要按平台/按用户限流，可在 ConcurrencyLimiter 之上加 key 隔离层。当前以"全局保护 LLM 服务方与服务器"为目标
