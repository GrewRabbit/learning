# 样例指纹缓存层

**日期**：2026-07-02
**类型**：新增
**影响范围**：缓存系统（HtmlCache 接口、DualKeyHtmlCache、FsHtmlCache、Orchestrator、problem-fetchers/types）

## 变更背景

原有缓存系统使用双层 key 设计（primary key + contentHash）。实测发现：用户文本方式输入与 platform（URL）方式输入同一道题时，因 fetcher 拼接的 markdown 格式与用户手输格式不同（标题带不带题号、样例章节名不同、代码块包裹格式不同），导致 contentHash 不匹配，文本方式无法命中 platform 方式已生成的缓存，触发重复 LLM 调用（耗时 + 消耗额度）。

实测数据（B3614 栈模板题）：全文 hash 不匹配（miss），但样例代码块内容 hash 完全一致。因此新增"样例指纹"缓存层，作为 contentHash 的补充查询路径，使文本/图片输入方式能命中 platform 方式已生成的缓存。

## 变更内容

### 样例指纹提取（problem-fetchers/types.ts）

- 新增 `extractSampleFingerprint(content: string): string` 函数
- 两步提取：第一步识别"样例"章节范围（`^## ` 含"样例"二字的标题起始到下一个 `## `），无则降级全文；第二步在范围内提取代码块，去除开头 ``` 及可选语言标记（```cpp 等）和结尾 ```，normalizeContent 后用 `|||` 拼接，SHA-256
- 无代码块返回空字符串（降级信号）

### HtmlCache 接口扩展（html-cache.ts）

- 接口新增 `getBySampleFingerprint(sampleFp: string): ServiceResult<{ contentHash: string } | null>`
- `getOrCompute` 新增可选参数 `sampleFp?: string`
- DualKeyHtmlCache 新增 `sampleCache: LRUCache<string, string>`（max=100, ttl=1h）
- getOrCompute 查询顺序：contentCache → sampleCache（命中则方案 B 回写 contentCache[currentContentHash]）→ compute
- sample 索引仅 validated=true 时回填，由 getOrCompute 内部写入（set 方法不变）

### FsHtmlCache 文件系统实现（fs-html-cache.ts）

- sample 索引文件路径：`{baseDir}/sample/{fp前2位}/{fp}.json`（分桶结构）
- 索引文件格式：`{ "contentHash": "xxx", "createdAt": "ISO时间" }`（与 primary 索引一致）
- sample 索引指向的 content 文件缺失时降级走 compute，compute 成功后覆盖失效索引实现自愈
- 写入采用 fire-and-forget 异步策略

### Orchestrator 改造（orchestrator.ts）

- `solvePlatform`：fetcher 抓取标准化后算 sampleFp，传入 getOrCompute
- `solveTextOrImage`：算 contentHash 后算 sampleFp，传入 getOrCompute
- primary 回填逻辑不变（方案 B：getOrCompute 命中 sample 时内部已用当前 contentHash 写 contentCache）

## 后续影响 / 注意事项

1. **已有缓存不迁移**：现有 content 文件无 sample 索引，新方案上线后 platform 方式不受影响（仍用 primary 索引），text 方式首次 miss → LLM 生成 → 自动建 sample 索引，之后能命中。不写迁移脚本（从 HTML 反向提取样例不可靠）。
2. **E2E B3614 用例**：当前 skip（已有 primary 缓存是 sample 索引功能上线前生成的）。需先用 URL 方式提交一次 B3614 生成 sample 索引，之后该用例自动启用。
3. **方案 B 回填机制**：getOrCompute 命中 sample 时内部用当前 contentHash 写 contentCache，Orchestrator 回填逻辑不变。这是 R1-001 阻塞问题的解决方案，确保 primary 索引指向的 contentHash 能命中 content 层。
4. **DualKeyHtmlCache vs FsHtmlCache 行为差异**：内存实现保留 sampleCache.delete 清理失效索引（同步无竞态）；文件系统实现依赖 writeSampleIndex 覆盖旧索引实现自愈（避免异步 unlink 与 writeFile 竞态）。两者都符合 spec（FR-007 说"可选择性删除"）。
5. **边界场景**：用户文本无代码块、样例数量不一致、image 识别格式不一致等情况会降级走 contentHash，不影响功能。
