# 样例指纹多候选与章节匹配扩展

**日期**：2026-07-05
**类型**：优化
**影响范围**：缓存系统（problem-fetchers/types、DualKeyHtmlCache、FsHtmlCache、Orchestrator）

## 变更背景

线上日志分析发现两个任务的样例指纹（sampleFp）匹配失败：

- **be86a3fd（platform URL 输入）**：洛谷 fetcher 抓取的 markdown 中样例章节用了三级标题 `### 样例 1`，旧 `extractSampleSectionRange` 仅匹配 `^## ` 二级标题，未识别到样例章节，兜底走全文（`sampleRangeLength=1137`，等于全文长度）。最终提取出 6 个代码块（3 组样例），`sampleFp=9972fa53...`
- **a2525a81（text 输入）**：用户文本含 `## 样例` 二级标题，正常截取样例范围（`sampleRangeLength=89`），提取出 2 个代码块（1 组样例），`sampleFp=6095a91d...`

两个指纹完全不同，导致 text 输入未能命中 platform 已生成的缓存。两个根本差异：
1. **章节匹配范围过窄**：仅匹配 `^## ` 二级标题，对洛谷 `### 样例 N` 三级标题失效
2. **样例数量差异**：用户只粘 1 组样例 vs fetcher 抓 3 组样例，单一 hash 必然不同

## 变更内容

### 方案 A：章节匹配扩展（problem-fetchers/types.ts）

- `extractSampleSectionRange` 标题正则从 `^## ` 扩展为 `^#{2,4}\s`（支持二/三/四级标题）
- 引入 `startLevel` 记录起始标题级别：
  - 子级别标题（`level > startLevel`）不结束范围，无论是否含"样例" —— 例如 `## 输入输出样例 #1` 下的 `### 输入 #1` / `### 输出 #1` 属于同一组样例的子标题，不应结束
  - 同级或更高级别标题（`level ≤ startLevel`）且不含"样例"时才结束 —— 例如 `## 样例` 后的 `## 输出格式` 应结束
- 用户手输格式 `## 输入输出样例 #1` 起始 + `### 输入 #1`/`### 输出 #1` 子标题的场景，旧逻辑遇 `### 输入 #1` 即结束，导致无法提取代码块；新逻辑能完整提取

### 方案 B：多候选指纹（problem-fetchers/types.ts）

- 新增 `SampleFingerprint` 接口：`{ readonly all: string; readonly first: string }`
- 新增 `EMPTY_SAMPLE_FINGERPRINT` 常量（all='', first=''，降级信号）
- `extractSampleFingerprint` 返回类型从 `string` 改为 `SampleFingerprint`：
  - `all`：所有样例块用 `|||` 分隔符拼接后 SHA-256（与原 sampleFp 等价，容错格式微差异）
  - `first`：仅前 2 块（第一组样例 输入+输出）拼接后 SHA-256（容错"用户只粘部分样例"场景）
  - 边界：无样例块时 `all === ''` 且 `first === ''`；仅 1 个块时 `all` 非空、`first === ''`（无法构成一组样例）
- 新增 `getCandidateFingerprints` 辅助函数（html-cache.ts 和 fs-html-cache.ts 各一份，避免循环依赖）：从 `SampleFingerprint` 提取非空候选列表 `[all, first]`

### DualKeyHtmlCache 适配（html-cache.ts）

- `HtmlCache` 接口 `getOrCompute` 的 `sampleFp?: string` 改为 `sampleFp?: SampleFingerprint`
- `getOrCompute` 第 2 步遍历多候选指纹查询 sampleCache：
  - 顺序 `[all, first]`，任一命中即触发 Plan B 回写并返回
  - 单候选失效（content 文件缺失）时清理该候选索引，继续查下一候选（自愈）
  - 全部候选均未命中时降级走 compute
- compute 成功 + validated=true 时遍历多候选写入 sample 索引（多候选全部写入）

### FsHtmlCache 适配（fs-html-cache.ts）

- `getOrCompute` 签名从 `sampleFp?: string` 改为 `sampleFp?: SampleFingerprint`
- 实现与 DualKeyHtmlCache 同步：多候选查询遍历 + 多候选写入遍历 + 日志字段调整
- Plan B 回写逻辑：任一候选命中即写当前 contentHash 对应的 content 文件，返回 cached=true

### Orchestrator 适配（orchestrator.ts）

- `solvePlatform` / `solveTextOrImage` 中 4 处日志字段调整：`sampleFp` → `sampleFpAll` + `sampleFpFirst` + `sampleFpAllShort` + `sampleFpFirstShort` + `hasSampleFp`

### 旧索引清理

- 清理 `data/gesp6/sample/` 目录下 14 个旧索引文件（旧索引存储的是字符串指纹，与新多候选格式不兼容）。目录现已清空，后续会按新格式自动重建。

## 后续影响 / 注意事项

1. **索引翻倍**：多候选写入使 sample 索引条目数翻倍（all + first 各一份），LRU max=100 仍足够（典型场景：100 道题约 200 条索引）。
2. **旧索引已清理**：`data/gesp6/sample/` 已清空，新请求会按新格式自动重建索引。短期内 text/image 输入会有一轮 miss → LLM 生成 → 建索引的过程，之后恢复命中。
3. **核心价值场景**：用户只粘 1 组样例 vs fetcher 抓 3 组样例时，`all` 候选不同但 `first` 候选一致（前 2 块相同）→ 命中 sample 索引，避免重复 LLM 调用。
4. **章节匹配兼容性**：扩展后支持洛谷风格（`### 样例 1` 三级标题）和用户手输风格（`## 输入输出样例 #1` + `### 输入 #1`/`### 输出 #1`），覆盖 90%+ 实际场景。
5. **边界不变**：无代码块、无样例章节等情况仍走 contentHash 降级，不影响功能。
