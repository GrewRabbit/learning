# 任务取消机制与轮询优化

**日期**：2026-07-03
**类型**：优化 + 新增
**影响范围**：API 接入层（/api/solve）、题目录入页（/solve）、任务队列（job-store）、编排层（orchestrator）

## 变更背景

前期分析发现三个不合理环节：
1. **用户取消/超时后服务端继续计算**：前端停止轮询后，后台 AI 调用仍继续执行，浪费 50-75% 的后续计算成本（尤其是修正循环的 2-3 轮 AI 调用）
2. **网络错误无限重试**：弱网下轮询 catch 块无重试上限，可能产生 100+ 次无效请求
3. **轮询间隔固定 3 秒**：5 分钟任务产生约 100 次请求，过于频繁

## 变更内容

### 任务取消机制（新增）

- **job-store.ts**：`JobStatus` 增加 `'cancelled'` 状态；新增 `cancelJob(id)` 函数，仅 `processing` 状态可取消，已完成/失败/取消的任务返回 false
- **route.ts**：新增 `DELETE /api/solve?jobId=xxx` handler，调用 `cancelJob` 取消任务；GET handler 增加 `cancelled` 状态返回 `GESP6_CANCELLED` 错误码
- **route.ts POST**：构造 `shouldAbort` 闭包传给 `orchestrator.solve`，闭包查 job-store 判断是否已取消；`.then` 回调检测取消标记，已取消的任务丢弃结果不写入 completeJob
- **orchestrator.ts**：`solve`/`solvePlatform`/`solveTextOrImage`/`compute` 均增加可选参数 `shouldAbort?: () => boolean`；在修正循环每轮开始前检查，若已取消则返回 `GESP6_CANCELLED` 错误
- **solve/page.tsx**：`handleCancel` 和客户端超时（>10分钟）时发送 DELETE 请求通知服务端；新增 `cancelJobOnServer` 辅助函数（静默失败不影响用户体验）

### 轮询间隔统一 10 秒

- **solve/page.tsx**：`POLL_INTERVAL_MS` 从 `3_000` 改为 `10_000`，正常轮询和网络错误重试统一使用 10 秒间隔

### 网络错误重试上限

- **solve/page.tsx**：新增 `MAX_NETWORK_ERRORS = 3` 常量和 `networkErrorRef`；连续网络错误超过 3 次后停止轮询并提示"网络连接不稳定，请检查网络后重试"；HTTP 请求成功（无论业务结果）重置计数

### 日志增强

- **job-store.ts**：`cancelJob` 成功时记录 `[JobStore] 任务已取消`，失败时记录 `[JobStore] 取消任务失败（不存在或非进行中）`
- **route.ts**：DELETE handler 记录 `[SolveRoute] 收到取消请求`；POST `.then` 回调检测到取消时记录 `[SolveRoute] 任务已取消，丢弃计算结果` 或 `[SolveRoute] 任务完成但已被取消，丢弃结果`
- **orchestrator.ts**：修正循环检测到取消时记录 `[Orchestrator.compute] 检测到取消标记，中止修正循环`

## API 契约变化

### DELETE /api/solve?jobId=xxx（新增）

- 成功取消：`200 { success: true, data: { cancelled: true } }`
- 任务不存在/已完成：`404 { success: false, error: { code: 'GESP6_JOB_NOT_FOUND', message: '任务不存在或已完成，无法取消' } }`
- 缺 jobId：`400 { success: false, error: { code: 'GESP6_INPUT_INVALID', message: '缺少 jobId 参数' } }`

### GET /api/solve?jobId=xxx（增加 cancelled 状态）

- cancelled：`200 { success: false, error: { code: 'GESP6_CANCELLED', message: '任务已取消' } }`

## 后续影响 / 注意事项

1. **取消粒度**：取消仅在修正循环每轮开始前检查，当前正在执行的 AI 调用无法中途取消（OpenAI SDK 限制）。最坏情况下取消后仍需等待当前 AI 调用完成（最多 120 秒），但能省下后续 1-2 轮修正的 AI 调用成本
2. **竞态处理**：计算完成与取消可能同时发生，POST `.then` 回调中做了双重检查（result.error.code === 'GESP6_CANCELLED' + job.status === 'cancelled'），确保已取消的任务结果不写入 completeJob
3. **前端取消行为**：用户点取消后前端立即停止轮询并恢复按钮状态，DELETE 请求异步发送不阻塞 UI。如果 DELETE 请求因网络问题失败，服务端任务仍会在 job TTL（30分钟）后自动清理
4. **轮询请求数降低**：间隔从 3s 改为 10s，5 分钟任务的轮询请求数从约 100 次降到约 30 次，减少约 70% 的网络开销
